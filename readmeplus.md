# CS_Wiki 프로젝트 학습 해설서

이 문서는 `README.md`의 빠른 실행 안내를 보완하는 독립 학습자료입니다. CS_Wiki를 처음 보는 사람도 프로젝트가 왜 필요한지, 자료가 어떻게 지식 문서가 되는지, 웹사이트가 어떤 과정을 거쳐 만들어지는지를 단계적으로 이해할 수 있도록 작성했습니다.

## 1. 이 프로젝트는 무엇인가

CS_Wiki는 컴퓨터 과학의 역사와 개념을 **출처와 연결 관계를 함께 보존하는 지식 탐색 시스템**입니다. 약 341개의 문서가 정규 소스, 참고 자료, 개념, 개체, 분석, 메타 문서로 나뉘어 있으며, 문서마다 안정적인 ID와 근거 목록을 가집니다.

### 해결하려는 문제

컴퓨터 과학 자료를 검색하면 서로 다른 문제가 한꺼번에 발생합니다.

- 원문과 요약이 섞여 무엇이 1차 자료인지 알기 어렵습니다.
- 같은 인물이나 개념이 여러 문서에서 다른 이름으로 등장합니다.
- 문서 사이의 선후 관계, 영향 관계, 반례를 본문만 읽어서는 놓치기 쉽습니다.
- 시간이 지나 파일명이나 제목이 바뀌면 기존 링크가 깨집니다.
- 사람이 작성한 Markdown을 웹에 공개할 때 누락된 링크나 잘못된 메타데이터가 뒤늦게 발견될 수 있습니다.

CS_Wiki는 이를 문서 규칙, 근거 계보(provenance), 지식 그래프(knowledge graph), 자동 검증, 정적 사이트 배포로 해결합니다. 따라서 단순한 문서 모음이 아니라 **어디에서 온 지식인지 추적하며 다음에 무엇을 읽을지 안내하는 탐색 시스템**입니다.

### 누가 어떻게 사용하는가

- **학습자**: 개념 페이지를 읽고 `관련 항목`과 학습 경로를 따라 기초에서 역사적 사례로 이동합니다.
- **연구자·작성자**: 원본 자료와 요약 페이지를 대조하고, `evidence_ids`로 근거 문헌을 확인합니다.
- **비개발자 편집자**: Markdown과 표준 frontmatter만 작성한 뒤 린트와 빌드 결과로 형식 오류를 확인합니다.
- **사이트 방문자**: 검색, 역사 시간축, 근거 계보 렌즈, 문서 관계 묶음을 통해 문맥을 탐색합니다.

## 2. 전체 작동 흐름

프로젝트는 원본을 보존하고, 가공된 지식 문서를 검증한 뒤, 브라우저가 읽을 정적 파일을 생성합니다.

```text
원본 자료(raw/)
        ↓ 읽고 보존
위키 지식 문서(wiki/)
        ↓ 매니페스트·스키마·링크·근거 검증
그래프·검색·역사·학습 경로 데이터
        ↓ Markdown을 HTML로 변환
정적 사이트(dist/)
        ↓ GitHub Actions가 업로드
GitHub Pages 공개 사이트
```

1. 사용자가 PDF, 웹 문서, Markdown 등의 원본을 `raw/`에 보존합니다.
2. 작성자가 원본을 읽고 `wiki/` 아래에 출처·개념·개체·분석 페이지를 만듭니다.
3. `scripts/wiki_manifest.mjs`가 모든 페이지의 frontmatter, ID, 위키링크, 근거를 하나의 매니페스트로 해석합니다.
4. JSON Schema와 linter가 문서 구조를 검사하고 maintenance 도구가 색인·개요·로그의 일관성을 점검합니다.
5. `site/`의 빌드 프로그램이 Markdown을 HTML로 변환하고 그래프·검색용 JSON을 생성합니다.
6. 생성물은 `dist/`에 놓이며, GitHub Actions가 검증을 통과한 `main` 커밋을 GitHub Pages에 배포합니다.

## 3. 디렉터리 구조

| 위치 | 일반적인 역할 | CS_Wiki에서 필요한 이유 | 수정 원칙 |
|---|---|---|---|
| `raw/` | 원본 자료와 첨부 자산 보관 | 나중에 요약을 다시 대조할 수 있는 기준점 | 원칙적으로 수정하지 않음 |
| `wiki/` | 사람이 읽는 Markdown 지식 문서 | 사이트의 실제 지식 원천 | 새 문서와 수정은 이곳에서 수행 |
| `wiki/sources/` | 소스·참고 자료 요약 | 문헌의 내용과 접근 방법을 분리해 기록 | frontmatter v2 준수 |
| `wiki/entities/` | 인물·조직·장소 | 이름이 다른 자료를 하나의 개체로 연결 | 내부 링크로 교차참조 |
| `wiki/concepts/` | 개념·이론·프레임워크 | 학습자가 재사용할 정의와 관계 제공 | 근거와 관계를 함께 기록 |
| `wiki/analyses/` | 비교·분석·종합 | 여러 문서를 연결한 해석 보존 | 주장과 근거를 분리 |
| `wiki/meta/` | 방법론·용어집 등 운영 문서 | 편집 규칙과 메타 지식 설명 | 그래프에서 보통 숨김 |
| `wiki/index.md` | 전체 페이지 카탈로그 | 사람이 목록을 빠르게 확인 | 생성 블록을 수동 편집하지 않음 |
| `wiki/overview.md` | 홈페이지용 전체 개요 | 주제와 현재 상태를 한눈에 제공 | maintenance로 재생성 |
| `wiki/logs/` | 작업별 원 기록 | 무엇이 언제 바뀌었는지 보존 | 작업마다 항목 추가 |
| `schema/` | JSON Schema와 스키마 설명 | 문서 형식을 기계적으로 합의 | 코드와 함께 검토 |
| `scripts/` | 검증·생성·보조 명령 | 반복 작업을 같은 방식으로 수행 | Node가 주 기준, Python은 보조 |
| `site/` | 콘텐츠 로드·빌드·브라우저 자산 | Markdown을 실제 웹 경험으로 변환 | 구현 변경 시 테스트 필요 |
| `tests/` | Node·Python 테스트 | 작은 기능과 회귀를 자동 확인 | 변경에 맞춰 테스트 보강 |
| `.github/` | GitHub Actions 워크플로 | PR 검증과 Pages 배포 자동화 | 배포 조건을 신중히 변경 |
| `dist/` | 생성된 정적 사이트 | 브라우저와 Pages가 제공하는 결과물 | 소스가 아니라 빌드 산출물 |
| `output/` | 보조 생성 출력 | 일부 도구의 중간·분석 결과 보관 | 필요할 때만 갱신 |
| `.obsidian/` | Obsidian 설정 | 로컬에서 Markdown을 편집·탐색 | 개인 설정과 공유 설정 구분 |

`raw/`는 **불변 원본**, `wiki/`는 **관리되는 지식**, `dist/`는 **재생성 가능한 결과물**이라는 세 층으로 이해하면 쉽습니다. 원본을 수정하지 않아야 나중에 요약의 정확성을 다시 확인할 수 있고, 결과물은 언제든 같은 소스에서 다시 만들 수 있습니다.

## 4. 핵심 데이터 모델

### 4.1 YAML frontmatter

Markdown 파일의 맨 위에 있는 `---` 사이의 YAML 블록을 frontmatter라고 합니다. 본문을 읽지 않고도 문서의 제목, 유형, 상태, 근거를 검색·검증할 수 있게 해 줍니다.

```yaml
---
schema_version: 2
id: concept-computing-capability
kind: concept
title: 컴퓨팅 능력
aliases: [계산 능력]
summary: 계산 장치가 문제를 표현하고 해결하는 능력을 설명하는 개념이다.
domains: [computer-science]
editorial_status: active
publication_visibility: public
graph_visibility: public
created: 2026-01-01
updated: 2026-07-26
review:
  mode: attested
  revision: sha256:...
  reviewed_at: 2026-07-26
  reviewed_by: editor
evidence_ids: [src-001, ref-002]
capability_layers: [computability]
---
```

### 4.2 주요 필드의 의미

| 필드 | 쉬운 의미 | 이 프로젝트에서의 역할 |
|---|---|---|
| `schema_version` | 문서 작성 규칙의 판 | v2 형식으로 해석할지 결정 |
| `id` | 문서의 주민등록번호 | 제목·파일명이 바뀌어도 `/docs/{id}/` 주소 유지 |
| `kind` | 문서 종류 | source, reference, concept, entity, analysis, meta 구분 |
| `title`, `aliases` | 대표 이름과 다른 이름 | 검색과 위키링크 별칭 처리 |
| `summary` | 목록만 읽어도 이해되는 요약 | 색인·검색 결과·웹 메타 설명에 사용 |
| `domains` | 주제 분류 | 컴퓨터 역사·아키텍처 같은 군집을 제공 |
| `editorial_status` | 편집 진행 상태 | draft → review → active → retired 흐름 표현 |
| `publication_visibility` | 공개 범위 | 공개 사이트에 내보낼지 결정 |
| `graph_visibility` | 그래프 표시 범위 | public/context/hidden으로 지도 노출 제어 |
| `evidence_ids` | 연결된 근거 묶음 | 문서가 어떤 소스·참고 자료를 사용하는지 표시 |
| `review` | 검토 상태와 revision | 내용이 검토된 버전을 식별 |
| `history` | 검증된 연도·시대 | 작성일이 아닌 역사적 사건을 시간축에 배치 |
| `capability_layers` | 컴퓨팅 능력의 층 | 계산 가능성·확장성 등 주제별 필터 제공 |

`kind: source`와 `kind: reference`는 `works`와 `access`를 추가로 가집니다. `works`는 실제 문헌의 계보(원 출판물·보조 문헌)를, `access`는 URL·로컬 파일·snapshot처럼 그 문헌을 어떻게 확인했는지를 기록합니다. 문헌 자체와 접근 수단을 분리해야 “무엇을 인용했는가”와 “어디서 다시 확인할 수 있는가”를 혼동하지 않습니다.

### 4.3 안정 ID와 revision

파일명은 사람이 읽기 좋게 바뀔 수 있지만 문서 ID는 바뀌지 않아야 합니다. 그래서 사이트의 정식 주소는 `/docs/{id}/`입니다. 이전 주소가 있으면 `redirect_from`으로 정적 리디렉션을 만들어 오래된 링크도 보존합니다.

`revision`은 문서의 핵심 메타데이터와 본문에서 계산한 SHA-256 해시입니다. 해시는 원문을 복원하는 암호화가 아니라, “검토한 내용과 지금 내용이 같은가”를 빠르게 확인하는 지문입니다. `review.mode: attested`와 함께 사용하면 검토 이후 본문이 몰래 바뀌었는지 탐지할 수 있습니다.

## 5. 전문용어 해설

아래 항목은 각 기술이 일반적으로 무엇에 쓰이는지와 CS_Wiki에서 왜 필요한지를 함께 설명합니다.

### Markdown

- **쉬운 정의**: 제목, 목록, 표를 기호로 표현하는 사람이 읽을 수 있는 문서 형식입니다.
- **일반적인 용도**: README, 위키, 블로그, 이슈처럼 텍스트 중심 문서를 작성합니다.
- **의의**: 특정 편집 프로그램에 종속되지 않고 Git으로 변경 내용을 비교하기 쉽습니다.
- **CS_Wiki의 필요성**: 지식 원문을 장기간 보존하면서 Obsidian과 웹 사이트에서 같은 내용을 사용하기 위해 선택했습니다.
- **사용 위치**: `raw/`의 원본 일부, `wiki/` 전 페이지, 프로젝트 설명 문서입니다.

### YAML과 frontmatter

- **쉬운 정의**: YAML은 사람이 읽기 쉬운 설정 표기법이고, frontmatter는 Markdown 상단의 메타데이터 영역입니다.
- **일반적인 용도**: 설정 파일, 배포 정보, 문서 속성, 자동화 입력값을 표현합니다.
- **의의**: 본문과 기계가 읽는 분류·상태를 분리하여 검색과 검증을 가능하게 합니다.
- **CS_Wiki의 필요성**: 341개 안팎의 문서를 같은 규칙으로 색인하고 상태·근거·공개 범위를 자동 처리해야 합니다.
- **사용 위치**: 모든 v2 위키 페이지의 `---` 블록, 특히 `schema/`의 예시입니다.

### JSON Schema

- **쉬운 정의**: JSON 데이터가 지켜야 할 필드와 값의 규칙을 선언하는 문서입니다.
- **일반적인 용도**: API 입력 검증, 설정 파일 검사, 데이터 계약(contract)을 공유하는 데 사용합니다.
- **의의**: 사람이 “대략 맞다”고 판단하는 대신 프로그램이 누락·오타·잘못된 타입을 일관되게 찾습니다.
- **CS_Wiki의 필요성**: 여러 작성자가 추가하는 frontmatter의 구조를 하나의 기준으로 유지합니다.
- **사용 위치**: `schema/wiki-page.schema.json`과 `scripts/wiki_manifest.mjs`를 통한 lint 과정입니다.

### 매니페스트(manifest)

- **쉬운 정의**: 여러 파일에서 읽은 정보를 한 번에 정리한 목록 또는 색인입니다.
- **일반적인 용도**: 패키지 목록, 빌드 입력 목록, 자산 목록, 데이터 카탈로그를 관리합니다.
- **의의**: 각 기능이 파일을 제각각 해석하지 않고 같은 사실을 공유하게 합니다.
- **CS_Wiki의 필요성**: ID·별칭·위키링크·근거를 lint, maintenance, 사이트 빌드가 동일하게 이해해야 합니다.
- **사용 위치**: `scripts/wiki_manifest.mjs`가 단일 기준이며 `site/content.mjs`가 이를 읽습니다.

### Linter와 maintenance check

- **쉬운 정의**: linter는 규칙 위반을 찾고, maintenance check는 생성 목록과 운영 상태가 맞는지 확인하는 검사입니다.
- **일반적인 용도**: 코드 스타일, 문서 형식, 링크, 생성 파일의 불일치를 커밋 전에 발견합니다.
- **의의**: 오류를 사용자에게 공개한 뒤가 아니라 작성 단계에서 고칩니다.
- **CS_Wiki의 필요성**: 누락된 ID, 빨간 링크, 고아 문서, 오래된 index가 사이트 품질을 즉시 떨어뜨리기 때문입니다.
- **사용 위치**: `npm run lint:wiki`, `npm run maintenance:check`, `scripts/wiki_lint.mjs`, `scripts/wiki_maintenance.mjs`입니다.

### 정적 사이트 생성기와 build

- **쉬운 정의**: Markdown과 데이터 파일을 미리 HTML·CSS·JavaScript 파일로 바꾸는 프로그램과 그 변환 작업입니다.
- **일반적인 용도**: 블로그, 문서 사이트, 제품 안내서를 서버 없이 배포합니다.
- **의의**: 방문 때마다 데이터베이스를 조회하지 않아 빠르고, 결과를 파일 단위로 검토·캐시할 수 있습니다.
- **CS_Wiki의 필요성**: 지식 문서를 Git으로 검토한 결과만 공개하고 GitHub Pages에서 저비용으로 제공하기 위해 사용합니다.
- **사용 위치**: `site/build.mjs`가 `dist/`를 생성하고 `npm run build`가 실행합니다.

### Node.js, ES Module, npm

- **쉬운 정의**: Node.js는 브라우저 밖에서 JavaScript를 실행하는 환경, ES Module은 `import`/`export` 방식, npm은 패키지와 명령을 관리하는 도구입니다.
- **일반적인 용도**: 웹 서버, 빌드 도구, 테스트, 자동화 스크립트를 실행합니다.
- **의의**: 브라우저와 같은 언어로 콘텐츠 처리·빌드·검증을 연결합니다.
- **CS_Wiki의 필요성**: 매니페스트, lint, 사이트 생성, 테스트가 하나의 실행 생태계에서 동작해야 합니다.
- **사용 위치**: `package.json`, `scripts/*.mjs`, `site/*.mjs`, `tests/*.test.mjs`입니다.

### Python 보조 도구

- **쉬운 정의**: Python으로 작성된 작은 프로그램이 특정 데이터 처리와 테스트를 보조합니다.
- **일반적인 용도**: 텍스트 분석, 파일 변환, 과학 계산, 테스트 자동화에 널리 쓰입니다.
- **의의**: 이미 검증된 생태계를 활용해 한 가지 작업을 간결하게 해결할 수 있습니다.
- **CS_Wiki의 필요성**: 폰트 서브셋과 일부 호환성·외부 링크 검사를 Node 주 흐름과 분리해 유지합니다.
- **사용 위치**: `scripts/subset_fonts.py`, `tests/test_*.py` 등입니다.

### JSON과 SHA-256

- **쉬운 정의**: JSON은 프로그램 사이에서 주고받기 쉬운 구조화 텍스트이고, SHA-256은 파일에서 계산하는 고정 길이 지문입니다.
- **일반적인 용도**: JSON은 API·설정·검색 데이터, SHA-256은 무결성·캐시·파일 식별에 사용합니다.
- **의의**: 브라우저가 필요한 데이터를 작고 예측 가능한 형식으로 읽고, snapshot이 바뀌었는지 확인할 수 있습니다.
- **CS_Wiki의 필요성**: 그래프·역사·검색 인덱스를 정적 파일로 제공하고 로컬 원본의 재현 조건을 보존합니다.
- **사용 위치**: `dist/data/`, manifest의 revision, `access`의 snapshot 해시입니다.

### GitHub Actions와 GitHub Pages

- **쉬운 정의**: GitHub Actions는 저장소 사건에 따라 명령을 실행하는 자동 작업이고, Pages는 정적 파일을 웹 주소로 공개하는 서비스입니다.
- **일반적인 용도**: 테스트·빌드·배포를 자동화하고 문서 사이트를 호스팅합니다.
- **의의**: 사람의 로컬 환경 차이를 줄이고, 검증된 커밋만 공개합니다.
- **CS_Wiki의 필요성**: PR은 검증만 하고 `main`은 Pages에 배포하는 안전한 흐름이 필요합니다.
- **사용 위치**: `.github/workflows/pages.yml`, `.github/workflows/external-links.yml`입니다.

### 지식 그래프와 provenance

- **쉬운 정의**: 지식 그래프는 문서를 점(node)과 관계(edge)로 표현한 지도이고, provenance는 정보가 어디에서 왔는지 기록한 계보입니다.
- **일반적인 용도**: 추천, 검색, 연구 데이터 계보, 영향 관계 분석에 사용합니다.
- **의의**: 문서를 차례로 읽는 것만으로 놓칠 수 있는 연결과 근거의 출발점을 보여 줍니다.
- **CS_Wiki의 필요성**: 개념·인물·자료의 관계를 탐색하고, 주장에 연결된 원자료를 다시 확인해야 합니다.
- **사용 위치**: `site/graph/`, `evidence_ids`, `## 관계`, 근거 계보 렌즈입니다.

### 정적 라우팅과 redirect

- **쉬운 정의**: 라우팅은 URL을 어떤 페이지 파일로 연결하는 규칙이고, redirect는 옛 주소를 새 주소로 안내하는 페이지입니다.
- **일반적인 용도**: 웹 앱의 화면 주소, 문서 버전 이전, 도메인 변경을 관리합니다.
- **의의**: 사용자가 링크를 통해 안정적으로 목적지에 도달하고 검색 엔진의 기존 주소도 보존됩니다.
- **CS_Wiki의 필요성**: 안정 ID 주소와 과거 유형별 주소를 함께 유지해야 문서명 변경이 탐색 이력을 깨뜨리지 않습니다.
- **사용 위치**: `site/build.mjs`의 `/docs/{id}/` 생성과 `redirect_from` 처리입니다.

### Playwright와 접근성 테스트

- **쉬운 정의**: Playwright는 실제 Chromium 브라우저를 자동 조작하는 테스트 도구이며, 접근성 테스트는 키보드·스크린리더 사용 조건을 검사합니다.
- **일반적인 용도**: 검색·로그인·반응형 화면·브라우저 회귀 테스트를 재현합니다.
- **의의**: 파일이 생성되었다는 사실만으로는 확인할 수 없는 실제 사용자 경험을 검사합니다.
- **CS_Wiki의 필요성**: 검색, 모바일 탐색, 지식 렌즈, 키보드 입력, no-JavaScript 경로가 함께 작동해야 합니다.
- **사용 위치**: `scripts/run_browser_tests.mjs`, `npm run test:browser`입니다.

### no-JavaScript 경로

- **쉬운 정의**: 브라우저에서 JavaScript를 실행하지 않아도 읽고 이동할 수 있는 HTML 기본 경로입니다.
- **일반적인 용도**: 검색 엔진 색인, 느린 네트워크, 보안 제한, 보조 기술 지원을 보완합니다.
- **의의**: 화면 효과나 동적 기능이 실패해도 핵심 문서 접근성을 보장합니다.
- **CS_Wiki의 필요성**: 지식 사이트의 기본 목적은 문서 읽기이므로 상호작용 코드가 없어도 본문과 링크가 남아야 합니다.
- **사용 위치**: `site/`가 생성하는 정적 링크와 브라우저 테스트 시나리오입니다.

### 폰트 서브셋(font subset)

- **쉬운 정의**: 실제 사이트에서 사용하는 글자만 남겨 웹폰트 파일을 작게 만드는 작업입니다.
- **일반적인 용도**: 다국어 사이트의 초기 로딩 속도와 저장 용량을 줄입니다.
- **의의**: 한글 전체 글꼴을 내려받지 않아도 페이지를 빠르게 표시할 수 있습니다.
- **CS_Wiki의 필요성**: 한국어 문서가 많고 정적 Pages 환경에서도 모바일 탐색 속도를 유지해야 합니다.
- **사용 위치**: `scripts/subset_fonts.py`, `npm run fonts:subset`, `site/assets/fonts/`입니다.

## 6. 문서가 만들어지는 방식

### 표준 작업 흐름

1. **원본 보존**: 자료를 `raw/`에 넣고 파일명·첨부 자산을 유지합니다.
2. **유형 결정**: 정규 소스인지 참고 자료인지, 또는 개념·개체·분석인지 정합니다.
3. **요약 작성**: `wiki/sources/`에 문헌의 핵심, 인용할 만한 구절, 접근 정보를 기록합니다.
4. **지식 연결**: 관련 개념·인물·분석 페이지를 만들거나 갱신하고 처음 언급에 위키링크를 붙입니다.
5. **근거 등록**: 문서가 사용하는 `src-NNN`·`ref-NNN`을 `evidence_ids`에 기록합니다.
6. **관계 기록**: 인과·선후·구현 관계는 `## 관계` 표에서 방향과 이유를 명시합니다.
7. **색인·로그 갱신**: maintenance 도구로 `index.md`·`overview.md`를 만들고 `wiki/logs/`에 원 기록을 남깁니다.
8. **검증**: lint, maintenance, 테스트, 빌드, 사이트 검증을 순서대로 실행합니다.

### 실제 예시: 배비지와 러브레이스 자료

`raw/컴퓨팅의 기원 - 배비지와 러브레이스.md`를 추가했다고 가정해 보겠습니다.

```text
raw/컴퓨팅의 기원 - 배비지와 러브레이스.md
        ↓ 원문 정독·사실 추출
wiki/sources/컴퓨팅의 기원 - 배비지와 러브레이스.md
        ↓ 근거 ID와 연결
wiki/entities/찰스 배비지.md
wiki/entities/에이다 러브레이스.md
wiki/concepts/프로그램 가능성.md
        ↓ 색인·그래프·사이트 빌드
dist/docs/{stable-id}/
```

소스 페이지는 “어떤 문헌을 읽었는가”를 설명하고, 개체 페이지는 배비지와 러브레이스의 역할을 여러 자료에서 합칩니다. 개념 페이지는 분석 가능한 일반 원리를 추출합니다. 이렇게 층을 나누면 원문 요약과 편집자의 해석을 서로 다른 페이지에서 검토할 수 있습니다.

## 7. 사이트 내부 구현

### 콘텐츠와 매니페스트

- `site/content.mjs`는 매니페스트가 읽은 위키 페이지를 사이트용 페이지 모델로 바꿉니다.
- `scripts/wiki_manifest.mjs`는 YAML, ID, 별칭, 본문 링크, 근거, revision을 해석하는 단일 기준입니다.
- `scripts/wiki_lint.mjs`는 이 매니페스트를 사용해 스키마·링크·섹션·중복을 검사합니다.

### 빌드와 검증

- `site/build.mjs`는 Markdown을 HTML로 렌더링하고 `/docs/{id}/` 라우트, 목록, 검색 데이터, 역사·학습·근거 그래프 데이터를 생성합니다.
- `site/markdown.mjs`는 Obsidian callout과 내부 `wiki-v2` 제어 주석을 웹 출력에 맞게 정리해 운영용 표식이 화면에 노출되지 않도록 합니다.
- `site/graph/`의 `model.mjs`, `schema.mjs`, `selectors.mjs`, `evidence.mjs`, `history.mjs`는 관계·근거·역사 데이터를 모델링하고 선택합니다.
- `site/verify-build.mjs`는 생성된 HTML·JSON의 라우트, 데이터 버전, 크기 예산, 내부 링크, 운영 정보 누출을 검사합니다.

### 브라우저 자산

- `site/assets/`에는 검색, 필터, 그래프 렌즈, 키보드 탐색에 필요한 JavaScript가 있습니다.
- `site/styles/`에는 레이아웃·색상·반응형·접근성 등 기능별 CSS가 있습니다.
- `site/serve.mjs`는 로컬에서 `dist/`를 확인할 간단한 서버를 실행합니다.

## 8. 지식 그래프와 탐색 기능

### 문서 관계

본문의 `[[위키링크]]`는 문서 사이의 읽기 연결을 만듭니다. 의미가 있는 방향 관계는 `## 관계` 표에 별도로 기록합니다. 한 행은 “현재 문서가 대상 문서에 대해 어떤 역할을 하는가”로 읽습니다.

```markdown
## 관계

| 관계 | 대상 | 설명 | 근거 |
|---|---|---|---|
| enables | [[저장 프로그램 컴퓨터]] | 프로그램 교체를 배선 변경에서 기억장치 갱신으로 바꾼다. | [[First Draft of a Report on the EDVAC]] |
```

### 네 연결 채널

같은 문서 쌍에 여러 연결이 생겨도 화면에서는 하나의 묶음으로 보여 주고, 내부에서 다음 네 채널로 구분합니다.

| 채널 | 포함 관계 | 의미 |
|---|---|---|
| `core` | `## 관계`의 의미 관계 | 편집자가 직접 설명한 인과·선후·구현 관계 |
| `guide` | `recommends`, `path_next`, 과거 `related` | 다음에 읽을 문서 안내 |
| `evidence` | frontmatter `evidence_ids`에서 생성 | 어떤 근거를 사용하는지 표시 |
| `trace` | 본문 언급에서 생성 | 문서 안에서 이름이 언급된 흔적 |

묶음으로 합치는 이유는 같은 두 문서 사이에 “선행한다”, “근거다”, “다음에 읽는다”가 동시에 존재할 수 있기 때문입니다. 연결을 따로 그리면 지도에 중복 선이 늘어나 핵심 의미를 파악하기 어려워집니다.

### 탐색 렌즈와 경로

- **근거 계보 렌즈**: 문서에서 소스·참고 자료로 올라가고, 다시 그 근거를 사용하는 하류 문서로 내려갑니다.
- **역사 시간축**: `history.publication_year`와 `history.event`의 검증된 연도를 사용해 문서 작성일과 역사적 시점을 구분합니다.
- **학습 경로**: 25개의 큐레이션 경로가 기초 개념에서 역사적 기계·소프트웨어·시스템으로 이동하는 순서를 제안합니다.
- **검색·필터**: 제목 prefix, 문서 유형, 도메인, 상태, capability layer를 조합해 필요한 문서만 좁힙니다.
- **정적 페이지네이션**: 고차수 문서와 근거 목록은 여러 페이지로 나누어 한 화면의 HTML 크기를 제한합니다.

## 9. 품질 보증과 안전장치

### 원본과 검토 상태

`raw/`는 불변입니다. 요약이 틀렸다면 원본을 덮어쓰지 않고 `wiki/` 문서를 수정하여 무엇을 다르게 해석했는지 기록합니다. `editorial_status`와 `review.mode`는 작성 중인 내용과 검토가 끝난 내용을 구분합니다. 내용 변경으로 기존 revision이 무효가 되면 `active`에서 `review`로 되돌리고 새 attestation을 남깁니다.

### 자동 점검 항목

- frontmatter 필수 필드와 허용 값
- ID·별칭 충돌 및 중복 관계
- 존재하지 않는 위키링크(빨간 링크)
- 들어오는 링크가 없는 고아 페이지
- `## 출처`, `## 관련 항목`의 위치와 추천 개수
- snapshot 파일의 SHA-256·바이트 수
- index·overview·log의 생성 표식과 페이지 수
- 생성 HTML의 내부 주석·절대 경로·비밀 정보 누출
- 정적 라우트, JSON 데이터 버전, 파일 크기 예산

### 테스트 층

1. **Node 단위 테스트**(`npm run test:site`): 매니페스트·그래프·Markdown 변환의 작은 동작을 검증합니다.
2. **Python 테스트**(`npm run test:python`): 보조 도구와 호환성 동작을 확인합니다.
3. **빌드 검증**(`npm run verify:site`): 실제 `dist/` 결과가 구조 규칙을 만족하는지 확인합니다.
4. **Chromium 테스트**(`npm run test:browser`): 검색·모바일·키보드·접근성·no-JavaScript 경로를 실제 브라우저에서 확인합니다.
5. **외부 링크 점검**(`npm run check:links`): 404·410과 401·403·429 같은 접근 제한을 구분합니다.

### PR과 main 배포를 나누는 이유

`.github/workflows/pages.yml`은 PR에서 검증과 빌드만 수행하고, `main`에 병합된 뒤에만 Pages 배포 단계를 실행합니다. 실험 중인 변경이 공개 사이트에 바로 노출되는 것을 막고, 검토된 커밋을 배포 기준으로 삼기 위한 선택입니다. 별도 워크플로는 주 1회 외부 링크 상태를 검사해 시간이 지나 사라진 자료를 알려 줍니다.

## 10. 직접 실행하는 방법

권장 환경은 Node.js 22와 Python 3.12입니다. Windows PowerShell에서 실행 파일 인식 문제가 있으면 `npm` 대신 `npm.cmd`를 사용합니다.

| 명령 | 목적 | 실행 시점 | 예상 결과 |
|---|---|---|---|
| `npm ci` | `package-lock.json` 기준 의존성 설치 | 처음 받았을 때·깨끗한 환경 | `node_modules/` 생성 |
| `npm run dev` | 빌드 후 로컬 서버 실행 | 문서와 화면을 함께 확인할 때 | localhost 주소 출력 |
| `npm run build` | Markdown·데이터를 `dist/`로 변환 | 변경 후 사이트 생성 | 정적 HTML·JSON 생성 |
| `npm run lint:wiki` | 문서 스키마·링크·관계 검사 | 위키 문서 변경 직후 | 오류가 없으면 성공 종료 |
| `npm run maintenance:check` | 색인·개요·로그 일관성 검사 | 생성 페이지를 확인할 때 | 불일치가 없으면 성공 종료 |
| `npm run check` | lint·maintenance·테스트·빌드·사이트 검증 묶음 | 병합 전 종합 확인 | 모든 단계 통과 |
| `npm run test:browser` | Chromium 사용자 흐름 검사 | UI 변경 또는 배포 전 | 브라우저 시나리오 통과 |
| `npm run check:links` | 외부 URL 상태 확인 | 자료 링크가 오래되었을 때 | 깨진 링크 목록 또는 성공 |

PowerShell 예시는 다음과 같습니다.

```powershell
npm.cmd ci
npm.cmd run lint:wiki
npm.cmd run maintenance:check
npm.cmd run build
npm.cmd run verify:site
npm.cmd run dev
```

`npm run test:browser:install`은 처음 브라우저 테스트를 실행하는 환경에서만 Chromium 런타임을 준비합니다.

## 11. 새 문서 추가 실전 튜토리얼

### 1단계: 원본 보존

원본 파일과 첨부 이미지를 `raw/`에 넣습니다. 파일을 수정하거나 재저장해 줄바꿈·메타데이터를 바꾸지 말고, 필요한 정규화는 위키 요약 페이지에서 수행합니다.

### 2단계: 문서 유형 선택

- 출판물·원자료 요약이면 `kind: source`
- 보충 문헌·외부 자료면 `kind: reference`
- 재사용 가능한 원리면 `kind: concept`
- 인물·조직·장소면 `kind: entity`
- 여러 자료를 비교·종합하면 `kind: analysis`

### 3단계: frontmatter 작성

`id`는 소문자 ASCII slug로 한 번 정하면 바꾸지 않습니다. `summary`는 본문 첫 문장을 잘라 쓰지 말고, 검색 결과만 읽어도 범위와 핵심이 드러나는 독립 문장으로 씁니다. 공개하지 않을 운영 문서는 `publication_visibility`와 `graph_visibility`를 알맞게 설정합니다.

### 4단계: 본문과 관계 작성

본문은 한국어를 기본으로 하고 중요한 전문용어는 영어를 병기합니다. 처음 언급하는 관련 문서는 `[[위키링크]]`로 연결합니다. 의미 관계가 있으면 `## 관계` 표에 대상·설명·직접 근거를 작성하고, 하단에는 `## 출처`와 마지막 `## 관련 항목`을 둡니다.

### 5단계: 검증하고 사이트에서 확인

```powershell
npm.cmd run lint:wiki
npm.cmd run maintenance:check
npm.cmd run build
npm.cmd run verify:site
npm.cmd run test:browser
```

오류가 있으면 메시지에 표시된 파일과 필드를 먼저 고칩니다. 빌드가 성공하면 `npm run dev`로 브라우저에서 문서 주소, 검색, 관계 렌즈, 모바일 화면을 확인합니다.

### 6단계: 로그 기록

`wiki/logs/`에 작업별 Markdown 로그를 추가하고 생성 목록인 `wiki/log.md`를 갱신합니다. 로그에는 변경한 페이지, 사용한 원본, 후속 관련 항목을 남겨 나중에 작업의 이유와 범위를 재구성할 수 있게 합니다.

## 12. 설계상의 선택과 한계

### 왜 데이터베이스 대신 Markdown과 Git인가

Markdown은 사람이 직접 읽고 편집할 수 있고 Git은 줄 단위 변경 이력과 검토를 제공합니다. 연구 노트처럼 내용 자체를 장기간 보존해야 하는 프로젝트에서는 전용 데이터베이스보다 이식성과 복구성이 좋습니다. 반면 복잡한 실시간 편집 권한, 대규모 동시 쓰기, 고급 트랜잭션에는 적합하지 않습니다.

### 왜 동적 서버 대신 정적 사이트인가

정적 사이트는 빌드 시 HTML을 미리 만들므로 서버와 데이터베이스 운영 부담이 작고 Pages에서 바로 제공할 수 있습니다. 캐시와 보안 표면도 단순합니다. 대신 새 문서가 공개되려면 다시 빌드해야 하고, 개인화된 로그인·실시간 댓글 같은 기능은 별도 서비스가 필요합니다.

### 왜 원본과 가공 문서를 분리하는가

원본을 보존하면 요약과 해석을 다시 대조할 수 있고, 편집 과정에서 실수로 증거가 사라지지 않습니다. 그 대가로 같은 사실이 원본·요약·개념 페이지에 나뉘므로 `evidence_ids`와 링크를 부지런히 관리해야 합니다.

### 왜 근거와 관계를 별도로 모델링하는가

근거는 “이 문서가 어떤 자료를 사용하는가”이고 관계는 “이 문서가 다른 문서와 어떤 의미적 역할을 맺는가”입니다. 둘을 한 목록에 섞으면 출처와 해석의 차이가 흐려집니다. 분리 모델은 근거 계보와 개념 지도를 각각 정확하게 보여 줍니다.

### 앞으로 확장할 수 있는 영역

문서 수가 늘어나면 그래프 페이지네이션과 prefix 검색 조각을 확장할 수 있습니다. 이후에는 더 세밀한 주장 단위 인용, 다국어 요약, 변경 영향 분석, 링크 보존 서비스 등을 검토할 수 있지만, 현재 스키마의 “문서 전체 근거 묶음” 의미를 깨지 않는 범위에서 설계해야 합니다.

## 13. 문제 해결 안내

| 증상 | 먼저 확인할 것 | 해결 방향 |
|---|---|---|
| lint 실패 | 오류 파일·필드·줄 번호 | frontmatter 필수 필드, 허용 enum, 링크·섹션 수정 |
| ID·별칭 충돌 | 다른 문서의 `id`와 `aliases` | 안정 ID는 새 값으로 정하고 별칭은 하나만 유지 |
| snapshot 해시 불일치 | `access`의 경로·바이트 수·SHA-256 | 원본을 덮어쓰지 말고 올바른 snapshot을 다시 보존 |
| maintenance 실패 | 생성 표식과 `wiki/logs` 목록 | `npm run maintenance:generate` 후 로그 목록을 확인 |
| 빌드 결과가 이상함 | `dist/`의 라우트와 `site/verify-build.mjs` 출력 | stale 산출물을 지우기보다 소스와 빌드 규칙을 점검 |
| 페이지 경로 404 | `id`, `SITE_BASE`, `redirect_from` | `/docs/{id}/`와 Pages base path 설정을 일치시킴 |
| 브라우저 테스트 실패 | Chromium 설치·콘솔·뷰포트 | `npm run test:browser:install`, 로컬 서버, 반응형 CSS 확인 |
| 외부 링크 차단 | HTTP 상태가 401/403/429인지 | 링크 소실(404/410)과 접근 제한을 구분해 기록 |
| 한국어 글자가 깨짐 | 폰트 서브셋 목록 | 사용 글리프를 포함해 `npm run fonts:subset` 재생성 |

운영 중에는 오류 메시지를 숨기지 말고 `wiki/logs/`에 원인과 조치 결과를 남기는 것이 중요합니다. 그래야 같은 문제가 다시 발생했을 때 해결 시간이 줄어듭니다.

## 14. 용어 사전과 명령어 요약

### 비개발자용 핵심 용어

| 용어 | 한 문장 설명 |
|---|---|
| 원본(source) | 요약·해석의 기준이 되는 최초 자료 |
| frontmatter | 문서 맨 위에 붙는 기계용 속성 묶음 |
| 스키마(schema) | 문서가 지켜야 할 형식 규칙 |
| 매니페스트(manifest) | 여러 문서의 ID·링크·근거를 모은 색인 |
| 린트(lint) | 규칙 위반을 자동으로 찾는 검사 |
| 빌드(build) | 소스 문서를 공개용 파일로 변환하는 과정 |
| 정적 사이트(static site) | 미리 생성한 HTML 파일을 제공하는 웹사이트 |
| 라우트(route) | URL과 실제 페이지를 연결하는 규칙 |
| 그래프(graph) | 문서와 문서 사이의 관계 지도 |
| provenance | 정보가 어느 자료에서 왔는지 나타내는 계보 |
| revision | 검토한 문서 버전을 나타내는 지문 |
| snapshot | 특정 시점에 보존한 로컬 자료 복사본 |
| CI | 커밋·PR마다 자동으로 검증하는 작업 흐름 |
| 접근성(accessibility) | 다양한 사용자가 키보드·보조기술로 이용할 수 있는 정도 |

### 프로젝트를 읽는 추천 순서

1. 이 문서의 1~3장에서 목적과 디렉터리 구조를 이해합니다.
2. 4~5장에서 frontmatter와 주요 기술 용어를 확인합니다.
3. 6장에서 원본이 지식 문서로 변환되는 흐름을 따라갑니다.
4. 7~9장에서 사이트 구현과 품질 안전장치를 살펴봅니다.
5. 10~11장의 명령과 튜토리얼로 작은 문서를 직접 추가해 봅니다.
6. 12~14장에서 설계의 장단점과 문제 해결법을 복습합니다.

이 순서를 따르면 코드를 먼저 이해하지 않아도 “왜 이 파일이 존재하는가”를 먼저 파악한 뒤 필요한 구현 세부로 내려갈 수 있습니다.
